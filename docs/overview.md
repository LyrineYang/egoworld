# 项目复盘与当前状态

复核日期：2026-10-24。Git 基线为 1f82263，当前工作区包含大量尚未提交的实现与新文件。
本文件区分原始目标、已有实现、本轮补充和待验证事项；不将代码存在视作模型验收通过。

## 1. 原设计实际想做什么

主要原文：[最初实施计划](archive/plan.md)、[早期讨论](archive/design/memory.md)、
[技术栈笔记](archive/design/tech-context.md)、[开发进度](archive/ops/progress.md)、[历史 runlog](archive/ops/runlog.md)。

原目标是将第一视角视频转换为可供下游研究使用的结构化数据：实例分割、人手姿态、物体位姿与机器人手映射。
硬件假设是单台 4×H100 / 128 核 CPU，原始视频约 30 秒至 2 分钟；TB 级处理是目标规模，不是已完成实验。

早期讨论还包含物体运动、场景切分、手/物体 mask 和场景重建这几类任务，而不只是四个模型的输出。
其中“物体运动”并未定义成当前已实现的速度、接触或跨片段轨迹要求。

原讨论的四层愿景与当前取舍：

| 层 | 原来设想 | 当前选择 |
| --- | --- | --- |
| 存储 | 不可变对象存储、Parquet/Lance、共享内存交换 | 单服务器共享本地路径、Parquet/NPZ、SQLite 与 Ray 引用；未接 S3/Lance |
| 计算 | 预热的模型 actor 池，CPU 解码/几何与 GPU 重叠 | 已拆执行池；CPU 工作尚未充分从模型 worker 分离 |
| 调度 | 动态任务分发、反压，云端可扩容 | 中央完成事件调度与数量上限；未实现 work stealing/自动扩缩容/字节预算 |
| 观测 | 吞吐、GPU 忙/等、数据分布漂移、告警与状态日志 | 阶段日志/QC/汇总；持续利用率、分布漂移和自动告警待实现 |

早期讨论曾提 Redis/Kafka 与多机扩容；正式实施计划已将其排除，当前仍不引入。
“ObjectRef”也不应一概叫零拷贝：Python 对象的序列化、跨进程读取与 GPU 搬运仍可能有成本。

| 原设计部分 | 具体要求 | 当前解释或修正 |
| --- | --- | --- |
| 视频清单 | video_id、路径、时长、fps、尺寸、音频、checksum、split | 输入身份与处理范围的依据 |
| 片段清单 | clip_id、起止时间、源帧范围、重叠、状态、错误与重试 | 时间必须与帧范围一致；当前默认最长 15 秒 |
| 运行清单 | run_id、配置、代码/模型/数据版本、Parquet 与坐标设置 | 对结果来源和恢复兼容性负责 |
| 分割 | 源分辨率 COCO RLE mask；手和物体 | 当前是 DINO 检测 + SAM2 传播；SAM2 本身不能代替文本检测器 |
| 三维数据 | 人手 3D、物体 6D、人手到机器人映射 | 原设计没有完整定义模型之间的尺度、左右手和世界坐标融合 |
| 存储 | 每片段 masks / hand_pose / object_pose / mapping.parquet + meta；优先 Parquet，Lance 候选 | 当前增加实例、二维轨迹、Fast3R 相机与点云；未引入第二套存储系统 |
| 并行 | 每 GPU 一个串行 actor；CPU 与 GPU/Writer 流水重叠；有界队列 | 每个时序片段内部有序，不意味所有片段全局串行 |
| 容错 | 原子写、幂等、恢复、分类重试、默认 5/15/45 秒退避、dead-letter | 当前扩展为阶段级提交与恢复 |
| 质量与监控 | 吞吐、排队、延迟、GPU 利用率、失败率、mask 空结果；Prometheus/Grafana/DCGM | 当前基础日志/QC 可用，自动监控系统尚未接线 |
| 原验收设想 | 10–20 视频；GPU 利用率 >60%；失败率 <1% | 仍是实验目标，小样本跑通不能验证后两项 |
| 非目标 | 多机、Kafka/Redis、exactly-once | 当前继续保持 |

原文将 row_group_size 写成 256MB，但 PyArrow 此参数按“行数”解释；当前默认 65,536 行，不能沿用原单位。
原文提出 32–64 个 CPU worker，属于大服务器起点，不适合无测量地复制到单卡或 CPU 紧张机器。

后续笔记探索了 DROID-Splat、TransNetV2、CoTracker3、S3/MinIO、LanceDB；这些不是已实现清单。
Fast3R 出现在历史进度/runlog 的占位接线记录中，不能据此认定已实现 SLAM 或完整场景重建。
笔记中的 GroundingDINO 1.5 与当前使用的开源 SwinT OGC 配置也应区分。

## 2. 本轮工作前实际有什么

通过 git show HEAD 对照，而非只根据旧进度日志判断：

- 已有 CLI/manifest、Ray driver、SQLite 状态、Parquet 写入与 smoke 测试骨架。
- 已有 SAM2 + GroundingDINO 接线；四个其他算子的 run 仍返回空列表/空结果。
- 旧 driver 建立多个 GPU actor，已经可以跨片段/多 GPU 并发；每个 actor 内把一个片段的全部模型依次执行。
- GPU 任务完成后，driver 用 ray.get 取回整个结果，再交给单一 Writer；重试通过 time.sleep 暂停推进。
- 旧恢复以片段状态为主；模型、写盘和真实数据条件的验收证据不足。

因此，准确问题是“阶段职责集中、CPU 工作藏在 GPU actor 内、资源配比不清、恢复粒度粗”，而不是“全系统完全串行”。

## 3. 最近这阶段已推进的内容

对话中的推进顺序是：先把无 GPU 的安装、输入与 SAM2 测试入口打通；再接入四个模型和分阶段 driver；
最后在本次复核中重新检查完成度、简化输出含义、研究吞吐方案。后两者不能代替真实模型验收。

| 工作 | 现在具体是什么 | 证据边界 |

| 输入与分割输出 | 帧对齐有界片段、实例 ID/类别/分数、分开的 mask、二维轨迹与空结果 QC | SAM2 控制流测试；真实推理仍待测 |

## 4. “均已实现”应如何理解

可确认的是：五阶段适配与编排代码、契约和测试入口已写入工作区，基础调度链路经过测试。
**不能据此声称：五个真模型已跑通、输出符合真实标注精度、CPU 无瓶颈、单卡不会 OOM、或服务器高吞吐已达标。**
此外，接入四模型尚未实现命名的人手弯曲角、跨模型世界坐标融合、抓取/接触动作标签、完整 SLAM。

| 证据 | 最近观察 | 不能证明什么 |
| --- | --- | --- |
| 2026-10-23 完整回归（含真实 Ray 的替身测试） | 86 passed / 11 skipped | 真实 CUDA 推理、模型精度、Linux 服务器长期可靠性 |
| 2026-10-24 本次 CPU 复跑 | 84 passed / 13 skipped，6.33 秒 | 其中两个 Ray 测试本次未开启，不应当作重新通过 |
| Ray 故障测试细节 | 真 worker 退出、替换；推进 watchdog 的起始时间以触发超时分支 | 未真正等待 900 秒；未证明外部模型死锁和 CUDA 异常均可恢复 |
| API 替身测试 | HaMeR 裁剪/左右手、FP 注册后跟踪、Dex 状态隔离、Fast3R PnP 错误路径 | 上游安装/API/权重兼容性；替身可能与实际库不一致 |
| 本机 CPU IO 探针 | 当前转码路径及重复解码开销可直接观察，详见设计 | 不是任何服务器吞吐基准，也不是优化后的端到端对比 |

84/86 是测试用例数，包含参数化，不能解释为完成了 84/86 项需求。
本次复核由同一协作会话完成，不将其标成独立外部审查；独立验证执行方式见 testing.md。

## 5. 现在还缺什么

1. 按已经确认的五阶段范围准备服务器模型/输入资产；普通 RGB 可先关闭 FoundationPose，不接新硬件/复杂模型。
2. 锁定四套真实模型环境与资产，分别运行小样本，检查图像/几何结果而非只查非空。
3. 对所需分支跑完整单卡、重复运行与中断恢复，保留原始命令、日志、输出及版本。
4. 给 load / decode / preprocess / GPU / postprocess / write 分别计时，补足内存、线程和磁盘预算。
5. 按 [调度研究与建议](design.md) 做小规模对比，决定缓存策略、单卡模型驻留批次和多卡资源配比。

前一研究轮只修改文档。后续收尾轮已补充 launch、资产和分环境预检、工作目录/绝对路径处理与服务器操作文档；
schema 3 保持不变。当时本地完整回归为 99 passed / 11 skipped，包含真实 Ray 的模型替身链路；
新增服务器启动测试 13 项通过。真实 GPU/原生模型仍待服务器验证。
后续开发仍可跨分支推进。没有硬件证据的部分保持“待验证”，已确认的需求和独立代码不必等它才继续开发。
