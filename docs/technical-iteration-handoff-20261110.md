# EgoWorld 技术迭代交接

本文整理本轮开发对话、仓库代码、已发布实验记录和迁移清单，供继续开发、性能分析和演示使用。整理日期为 2026-11-10，日期及下述复跑时间按 Asia/Shanghai。文件名中的历史日期和运行 ID 沿用原值。技术基线为 `f174aed0959340acb3ec59b7f595a702790596cf`，工作分支为 `codex/v100-two-gpu-endurance`。

对话中的目标与约束在本文按决策记录保存，数值结论以链接的机器可读结果为依据。尚未定位到独立提交的早期修复按当前代码说明，避免给它们补写未经核实的提交号。

## 1. 设计初衷与评价目标

用户最初要求克隆 EgoWorld、了解项目现状，随后明确核心目标是在具身数据类型下做到处理更快、清洗更准。可追溯、可复用的数据生产流程是实现这一目标的工程基础。最终评价要同时看端到端墙钟、每秒达标产出、误拒率和漏拒率。

具身数据的价值随任务而变化。无手片段可能有场景重建价值，静止接触帧可能有操作学习价值。任务准入、模型推理和最终质量检查需要各自保留理由与阈值。通过文件能读取、结构完整或数值有限的检查之后，还要用独立标签或几何约束判断内容是否达标。

项目以离线数据处理为主。用户选择所需的手、物体、场景或机器人输出，recipe 将其展开为模型依赖。相同输入、资产、参数与上游产物身份成立时，阶段结果可以恢复和复用。坐标系、单位、左右手、尺度和变换方向需要显式记录，时间戳对齐只是后续几何融合的一个条件。[项目定位](overview.md) · [数据 recipe](data-recipes.md) · [坐标与输出契约](outputs.md)

本轮用户确定的边界如下。

- 对照对象为 EgoWorld 与 Data-Juicer，先 CPU 和单卡验收，再进行两卡试跑。
- 同模型对照对齐输入、采样、清洗、模型及输出，使用独立标签冻结正式批次。
- 两卡希望达到超过 1.5× 的达标产出率，大小批量都需要实测。
- 长测配对的预算为 10–30 分钟，最终两次配对各自控制在 30 分钟以内。
- 单卡和 CPU 诊断要保留 infra 证据，包含 Nsight、阶段计时和资源观测。
- 后续用户要求只聚焦两卡，并明确四卡扩展需要另行确认。
- 迁移范围仅 EgoWorld，上传目的地最终指定现有 GitHub 仓库。公开数据需满足转移授权，密钥和令牌排除。

## 3. CI、服务器与模型环境准备

### CI 的两个故障

用户首先要求解决缺少 `torch` 和 Ray 子进程无法导入 `test_pipeline_logic`。当前 SAM2 逻辑测试使用 `SimpleNamespace` 和 `nullcontext` 提供测试需要的 Torch 接口，避免逻辑夹具依赖完整 GPU 框架。真实模型环境仍安装对应 Torch。Ray 测试在生成的 fixture runner 中将测试目录显式加入 `sys.path`，再导入 `full_packet`，使子进程具备所需的模块搜索路径。

当前 GitHub workflow 安装项目开发依赖、Ray 与 FFmpeg，启用 CPU/Ray 测试，真实模型 smoke 由服务器实验单独承担。`9796298` 与 `f174aed` 的 GitHub Actions 均已核实为成功。服务器准备阶段记录过 57 项回归通过，首轮长测前记录为 64 项通过、1 项跳过，本次解码调整相关回归为 56 项通过、1 项跳过。三组测试覆盖不同，跳过项需随相应日志解释。[SAM2 测试](../egoworld/tests/test_sam2_logic.py) · [Ray 测试](../egoworld/tests/test_ray_integration.py) · [workflow](../.github/workflows/tests.yml) · [技术基线 CI](https://github.com/LyrineYang/egoworld/actions/runs/42724570803)

### 包源、反代与 glibc

服务器包源 403 发生在默认代理的 HTTPS CONNECT 阶段。用户说明网络通过反向代理到本机后，检查了已有转发的 HTTP CONNECT 与 SOCKS5 能力，安装阶段通过本机配置的代理和 CA 完成下载。接手时需要重新配置本地的 `HTTP_PROXY`、`HTTPS_PROXY`、`PIP_INDEX_URL` 与证书信任项，具体端口由当前反代决定。

宿主 glibc 2.27 无法满足部分 PyArrow wheel 的 ABI 要求。已有 `.venv/run-jammy` 在独立用户和挂载命名空间中使用 Ubuntu 22.04、glibc 2.35，并绑定项目、设备及必要的驱动库。此次复跑也必须通过这一入口加载 PyArrow。直接在宿主启动同一 Python 环境曾复现 `GLIBC_2.28 not found`，接手时应同时核对解释器和启动入口。

Data-Juicer 固定为 1.6.1，源码版本为 `09178e1e0ac76cfbfe11232d66244e1ccc5add6f`。`.venv/dj-jammy` 承担共享模型对照，`.venv/dj-native-jammy` 用于原生产品验收。SAM2、HaMeR 和 DexRetarget 有独立 runner 环境。依赖版本与固定清单已随公开交接包保存，服务端原记录位于 `output/server-v100/prep/`。[环境与启动](server.md) · [依赖组织](../egoworld/env/README.md)

### 资产与真模型 smoke

用户提供了 `MANO_RIGHT.pkl`、`MANO_LEFT.pkl` 和 `info.txt`。准备记录显示 RGB 路径的 19 项静态资产检查通过，左右 MANO 中性姿态均得到 778 个有限顶点，HaMeR 和 WiLoR 接入了已核验右手资产。MANO 需要按个人授权从原附件或授权下载恢复。权重和原始数据的公开交付范围见 Release 中的 `omissions.csv`。

服务器采用 V100 32 GB，已验证 FP16 路径。该硬件不支持本次所需的原生 BF16 路径，因此 Fast3R 等模型的实际启用需要独立验收。SAM2 可选 CUDA 连通域扩展在填洞步骤发生段错误，环境采用 `SAM2_BUILD_CUDA=0` 重装同一版源码，使用无该扩展的路径。配对双方使用相同安装方式。HaMeR 离屏 EGL 配置与 CUDA 模型计算分别设置，迁移时 EGL 设备编号需要重新探测。

RGB 3 秒链路曾完成 SAM2 30 帧、HaMeR 6 行手姿态和 DexRetarget 6 行 Allegro 右手关节输出，16 个关节的 URDF 限位与指尖正向运动学检查通过，同一运行的恢复复用也已验收。这是模型接入的工程检查，正式质量结果来自后续独立标签批次。

## 4. 流水线实现思路

基本路径为输入筛选、manifest 构建、clip 准备、模型推理、Writer 提交以及 recipe 导出。SAM2/GroundingDINO 提供实例掩码与轨迹，HaMeR 提供人体手部参数，DexRetarget 将手姿态映射为机器人关节。FoundationPose 与 Fast3R 的资产和几何前提分别记录在各自配置中。

阶段的 durable receipt 记录产物及身份。下游在上游有效提交后执行，恢复时验证已有产物。模型权重可在 worker 内常驻，clip 的时序状态按 clip 生命周期管理。清洗拒绝、branch filter、质量不达标、执行失败和空输出是不同的状态，报告需保留对应原因。[阶段执行](throughput-execution.md) · [缓存与清洗](cleaning-and-cache.md)

已有优化思路主要围绕减少重复工作与保持资源有界。

| 思路 | 设计理由 | 已验证范围或约束 |
| --- | --- | --- |
| 模型常驻与按阶段调度 | 降低多 clip 的重复加载和换模成本 | 历史本机与 V100 配对均有证据，收益随批量变化 |
| 有限活动 clip 与准备预算 | 限制同时在途的数据和内存占用 | 当前两卡实验配置 `max_active_clips=12` |
| CPU 准备、推理、写出重叠 | 释放等待中的 GPU 或工作槽位 | 通用阶段拆分和本次本地常驻实验执行器各有入口 |
| 按内容复用源码导入解析 | 减少每个导出重复进行的源码分析 | 对照双方共同采用，源码变化仍要改变身份 |
| 可信资产登记 | 固定且已核验的资产减少重复完整哈希 | 首次登记成本单列，迁移后重建登记或用严格哈希 |
| 阶段与派生产物缓存 | 恢复和复用已经验证的工作 | 本轮正式新结果配对关闭跨运行结果缓存 |
| 按任务的 branch admission | 在缺少必要上游结果时减少无效计算 | 需保留任务相关原因，正确性随反例检查 |

两卡优化执行器属于本地研究路径。`two_gpu_stream.py` 通过受限数量的本地阶段进程、并发 clip 和 receipt 连接各阶段。小批次采用 SAM2 与 HaMeR 分卡的 pinned 布局，大批次让两卡分别拥有两类常驻模型的 dual 布局。Data-Juicer 采用两个真实 `DefaultExecutor`，统一筛选后分配互斥 clip。将研究路径变成通用分布式执行器仍需补齐更广泛的故障、恢复和不同 DAG 验收。[EgoWorld 两卡执行器](../egoworld/experiments/two_gpu_stream.py) · [Data-Juicer 分片](../egoworld/experiments/two_gpu_shards.py)

## 5. 数据冻结与比较契约

CPU 正例为 12 段带官方相机和手部标签的 EgoDex 视频，逐段核对标签长度与解码帧数，另有 16 个负例。GPU 正例使用 FreiHAND 官方评估标签，每张图编码为三帧，评分取中间帧。手侧正确且腕部相对 MPJPE 不高于 20 mm 才计为达标手。手部几何质量与清洗误拒分别计数，因此 785/864 达标和清洗误拒 0/864 可以同时成立。

单卡正式批次有 12 个正例，另设不重叠的 12 张留出集。96 张与 864 张批次依冻结方案排除先前使用的样本，864 张另有 6 个故障输入。后续复跑复用全部 870 个输入的路径顺序与 SHA-256、原 recipe 和评分策略。样本身份与生成来源见公开语料记录。[冻结语料](benchmarks/v100-2026-11-09/corpora.json)

同模型配对要求采样、模型资产、精度、清洗、QC、输出要求和缓存策略对齐。端到端从框架入口计到产物提交及进程退出。配对窗口还覆盖切换和审计。输出审核比较阶段表、掩码、轨迹、数组、手和机器人导出及 QC，允许表行顺序不同，逻辑字段和数组按精确一致检查。NVML 同时记录资源与外部作业。CPU 的达标单位为视频段，GPU 的达标单位为手。[配对契约](equal-work-benchmark.md) · [完整产物审计](../egoworld/experiments/matched_audit.py)

原生产品对比允许各框架选择原生模型，应在共同输出任务和独立标签上比较质量与成本。两卡固定模型测试的收益仅对应已冻结的工作量。真实视频中的运动、遮挡、连续跟踪和 RGB-D 场景仍需要新的独立数据验收。

CPU 和单卡的墙钟取各端五轮中位数，表中配对比值使用已归档的配对统计，因此与两个墙钟中位数直接相除可能略有不同。两卡各档均只有一对有效记录。

**CPU 清洗。** 两端误拒均为 0/12、漏拒为 4/16，漏掉的是像素相同的改封装副本。随后做包级去重原型的三轮消融，EgoWorld 中位耗时从 31.27 秒降到 28.97 秒，漏拒降为 0/16，正例全部保留。这个原型为“更准且更快”提供局部证据，其覆盖范围和默认启用策略仍需进一步验证。[CPU 记录](benchmarks/v100-2026-11-09/cpu.json)

**单卡。** 正式样本两端均 12/12 达标，平均腕部相对 MPJPE 为 10.22 mm。独立留出集均为 10/12 达标、12.77 mm。单卡收益接近 1，促使研究转向启动、流水线组织和主机供给的分项诊断。早期共享卡与中断尝试随正式结果保留，计时资格结合负载审计解释。[单卡记录](benchmarks/v100-2026-11-09/single-gpu.json)

**两卡前期。** 直接增加 worker 的收益接近 1。阶段 pinned 布局与可信资产登记的消融显示，在同布局下登记将 127.53 秒降到 113.87 秒，首次登记约 13.24 秒需单列。随后的本地常驻阶段执行与双方共同的源码解析复用，形成小批 1.885×、96 张 1.634× 的结果。96 张两端均 93/96 达标、MPJPE 12.12 mm，误拒 0/96、漏拒 0/6，完整输出一致。外部作业影响的试跑保存在诊断字段中。[两卡试跑与消融](benchmarks/v100-2026-11-09/two-gpu.json)

**首轮长测。** 配对总窗口 27 分 11 秒。两端均 785/864 达标、MPJPE 12.57 mm，误拒 0/864、漏拒 0/6。每秒达标手为 1.257 和 0.852。审计覆盖 864 个 clip，采样期间两端均未观察到外部 CUDA 作业。1.476× 低于用户期望的 1.5×。[首轮长测](benchmarks/v100-2026-11-09/endurance.json)

**后续复跑。** 2026-11-10 07:25:19 至 07:54:57，配对和审计共 29 分 38 秒。启动前等待四分钟后仍没有两张空闲卡，沿用用户允许有空间时使用服务器 GPU 的授权，选择各有约 14 GiB 余量的 V100 0 和 2。所有 870 条清洗判定与拒绝原因一致，2,592 条 mask、每类 2,694 行手和机器人导出及其他阶段产物逐值一致。独立质量指标与首轮相同。计时结束后另对原长测 EgoWorld 产物做逐值回验，也通过。本轮 1.444× 是共享环境实测，空闲卡的优化后验收尚缺。[复跑结果](benchmarks/v100-2026-11-09/endurance-followup.json)

## 7. 为什么长测收益下降，优化做了什么

96 张时模型流水线耗时为 85.59 秒对 154.21 秒，864 张时为 441.95 秒对 730.39 秒。流水线比值由 1.802× 降为 1.653×。随着批次扩大，Data-Juicer 的固定加载开销得到摊薄，EgoWorld 对启动重叠的相对收益随之收窄。

EgoWorld 清洗与导出合计从 20.96 秒增到 175.07 秒，占端到端墙钟从 19.2% 升到 28.0%。这两段两端的耗时接近，因而稀释端到端比值。两档变化的算术分解给出约 −0.111× 来自流水线相对比值变化、−0.053× 来自流水线墙钟占比变化、+0.006× 来自其余段相对耗时变化。固定成本和样本分布的独立因果贡献仍需专门消融。

首轮 864 张的 SAM2 中位服务时间 0.918 秒、中位排队 4.089 秒。HaMeR 与 DexRetarget 中位服务为 0.272 和 0.141 秒，排队约 1 毫秒。SAM2 成为优先检查的临界阶段，其服务时间包含 GroundingDINO、视频准备和写出。

已有单卡留出集 Nsight 中，CUDA kernel、拷贝及 memset 区间并集占完整 trace 的 3.93% 和 4.79%，两端主机与设备间搬运约 9.85 GB 和 9.93 GB。trace 包含冷启动。该证据支持排查主机供给和同步，864 张瓶颈排序则来自两卡阶段记录。[Nsight 证据](benchmarks/v100-2026-11-09/profiling.json)

本次发现 OpenCV 4.11 的 FFmpeg 后端默认每次打开短 clip 分配 16 个解码线程。50 个三帧视频、三轮微测中，单次打开与解码从约 38–39 毫秒降至约 17 毫秒，150 个独立帧的像素哈希一致。实现增加 `--sam2-decoder-threads`，由冻结计划记录，只在 EgoWorld SAM2 子进程中设置 `OPENCV_FFMPEG_THREADS`。实验使用值 1，普通调用保留默认行为。额外增加 `--input-plan`，直接复用原来的正负样本顺序与评分策略。

本轮两端模型流水线实际为 509.60 秒和 818.13 秒，高于首轮。V100 2 在两臂的所有采样中均有外部计算，V100 0 的负载也随运行变化。微测的解码改善已验证，优化在空闲双卡端到端墙钟上的净收益仍待实测。[详细复盘与重跑命令](v100-endurance-followup.md)

## 8. 100 TB 估算及适用条件

100 TB 按十进制计量，假设平均编码码率 20 Mbit/s，则约有 11,111 小时素材。若两端先形成相同的 2 帧/s 模型输入，对应约 8,000 万等价帧。按首轮空闲双卡的三帧负载端到端速率折算，EgoWorld 约 223 天，Data-Juicer 约 329 天，资源均为两张 V100 全天运行。

若优化在空闲卡每 864 张净省 10–28 秒，并且 Data-Juicer 保持历史墙钟，EgoWorld 的同口径估算约为 213–219 天，产出比约 1.50–1.55×。按本轮共享配对换算则约为 249 天和 360 天。这里的节省范围来自微测条件假设，尚缺空闲双卡的确认。

一次顺序读取 100 TB，在有效吞吐 200 MB/s、500 MB/s、1 GB/s 下约需 5.79、2.31、1.16 天。真实工期还取决于全解码要求、采样和拒绝比例、连续视频长度、分辨率、存储访问及输出量。当前三个相同图像帧的负载对长时跟踪和大规模数据调度的覆盖有限，目标数据上的分层试跑是后续校准依据。[情景表与计算结果](v100-endurance-followup.md#100-tb-量级预估)

## 10. 接手开发、复现与上传

本地直接从实验分支接手，Git 克隆会取得该分支源码及可达历史。首批 Release 的校验清单对应其固定附件。

```bash
git clone --branch codex/v100-two-gpu-endurance https://github.com/LyrineYang/egoworld.git
cd egoworld
git log -3 --oneline
python3 -m venv .venv/local
. .venv/local/bin/activate
python -m pip install -e '.[dev]'
egoworld --help
```

开发环境需要 Python 3.10 或以上。真模型 runner、CUDA、FFmpeg 和权重按环境文档重建。迁移后的路径、代理、CA、EGL 设备和可信资产登记需要重新定位。先完成 `egoworld doctor` 和各模型 smoke，再执行冻结与配对。原始输入、配置、资产和源码的哈希进入计划，改变实验条件时使用新 study 目录。

```bash
python egoworld/scripts/benchmark_two_gpu.py --study output/next-pair freeze \
  --recipe "$FROZEN_RECIPE" --corpus "$FROZEN_CORPUS" --input-plan "$FROZEN_PLAN" \
  --devices "$GPU_PAIR" --sam2-decoder-threads 1
timeout --signal=INT --kill-after=12s 1782s \
  python egoworld/scripts/benchmark_two_gpu.py --study output/next-pair run \
    --coordinator "$SAM2_PYTHON" --dj-python "$DATAJUICER_PYTHON" \
    --layout stream-checked-dual --budget-seconds 1760
```

上述变量需设置为本地已验收的文件、解释器和两张物理 GPU。原 V100 服务器的命令还需通过已有 `.venv/run-jammy` 兼容层执行。GPU 共享情况、失败、超时和环境稳定性记录与配对结果一起保留。

提交选定的代码或文档后，以下命令推送当前提交及其历史并核对远端。认证使用本机 GitHub 凭据配置。
