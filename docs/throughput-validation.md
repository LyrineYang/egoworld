# 吞吐实现与真实单卡验收（2026-11-01）

本轮完成分项观测、四模型内部 CPU/GPU 执行、有界交接、可追溯成本校准和实际调度对照。
这是单卡、固定样本的工程实现与验收；不代表第三部分所有风险已解决，也不代表服务器研究结论成立。
默认配置保持原启发式，输入缓存和阶段拆分默认关闭；所有实验使用独立配置快照，没有自动调整生产配置、精度、采样或输出。

完整接口见 [执行设计](throughput-execution.md)，逐项要求见 [目标台账](throughput-goal.md)，
机器可读证据见 [指标摘要](benchmarks/throughput-2026-11-01.json)。
逐次请求、响应、配置、输出、源码快照、日志和失败尝试保留在 `output/throughput-validation/`。

## 交付与行为

| 要求 | 交付 |
| --- | --- |
| 固定输入与复用 runner | replay 校验视频/清单/上游提交；gpu-probe 复用同环境常驻 runner，逐次记录冷调用、预热与热调用 |
| NVML 和性能历史 | 真实 UUID/驱动/设备显存、进程树 RSS、Torch allocator 分开记录；失败、争用和缺测明确保留；生产运行按 invocation 留历史 |
| 第五部分 B | 同一准备片段内共享按需帧、HaMeR 官方 crop 缓存、内容身份/损坏重建、LRU/条目/磁盘预算、memmap 复制后关闭及退出清理 |
| 第三部分的局部改造 | HaMeR CPU 官方裁剪与有界跨帧 batch；SAM2 阈值后二值 mask 一次 D2H、CPU 复用编码；Fast3R 官方输入/GPU/CPU PnP 分离；FP RGB-D 准备和注册/跟踪观测 |
| 执行边界 | CPU input → GPU infer → CPU post → Writer；跨片段重叠；最终 Writer 仍是唯一可靠阶段提交 |
| 预算与恢复 | 输入前预留结果及阶段临时盘额度，块与阶段硬文件字节上限；Writer 排空；四处失败重试、超时/中断清理与恢复 |
| 调度研究入口 | 显式 report 校准与 cost 策略；先硬约束/等待保护，再比较加载、服务和活动 prepared 额度退出价值；保留每次候选与选择理由 |

没有新增第二个生产后端，也没有模型并发共驻、自动扩缩容或后台改配置。
另一任务的 13 类输出配方、跨 run 阶段结果缓存、世界坐标附加数据和坐标修正已作为基线导入，
其工作区未被本轮开发覆盖。输入缓存、产品结果缓存和阶段临时块分别承担不同职责。

## 测量条件与版本

- 硬件：RTX 4060 Laptop 8 GiB；WSL/Linux，本机单 GPU，原有隔离模型环境。
- 短 RGB 输入：3 秒、30 帧、426×206；HaMeR 相同 frame_stride=5、batch_size=2，Fast3R 两视图、224 输入和相同精度，SAM2 相同提示与输出帧。
- FP：现有 3 帧 640×480 mustard RGB-D/网格；一个物体；不是多物体精度数据集。
- 每份模型报告：1 次冷调用＋1 次预热＋3 次热调用，seed=0；冷指新模型进程，不清空 OS/驱动缓存。
- 最终指标选择 12 份报告，共 60 次调用；36 次热输出对照包含基线自身波动。
- 调度矩阵在冻结 v3 源码运行；最终源码 v4 只补齐 HaMeR 基线路径的惰性 DataLoader crop/collation 计时，未改模型数值或调度。
  v4 已重跑 HaMeR 三种模式及四模型 split 预检，生成匹配最终源码的 `calibration-final.json`。
  其它三模型适配器及执行/调度文件在 v3/v4 完全相同；摘要逐报告保留源哈希。
- v1/v2 及继承 per_task 的早期调度尝试全部保留。per_task 对照不用于驻留窗口结论；中断尝试及配置原因有单独记录。

最终包源码哈希：`e94d1111efd4a19aff86fd2742a8b786374acc45614be8233ee780e614b26a19`。
冻结源码与模型/资产/输入/环境身份均可从报告反查；普通源码/资产变更后，旧校准会被拒绝，须显式重新预检。

## 单模型结果：局部收益与完整成本

单位为秒，表内均为三次热调用中位数。`split 步骤合计` 是 CPU/GPU/CPU worker 内同步墙钟之和，
`GPU 步骤` 仍可能含模型库的 CPU 工作。完整 trial 还包含 runner 协议、序列化、环境观测与 Writer；不能混用这三种口径。

| 模型 | baseline worker | profile worker | split 步骤合计 | split GPU 步骤 | 完整 trial：baseline → split |
| --- | ---: | ---: | ---: | ---: | ---: |
| fast3r | 2.480 | 2.654 | 2.677 | 0.329 | 3.083 → 4.719 |
| foundationpose | 10.291 | 9.429 | 10.310 | 10.214 | 10.766 → 12.290 |
| hamer | 0.389 | 0.433 | 0.399 | 0.279 | 0.871 → 2.161 |
| sam2 | 4.085 | 4.072 | 4.481 | 4.406 | 4.612 → 6.282 |

Fast3R 的 CPU PnP 移出 GPU worker 后，GPU 槽位占用明显下降；它的完整单任务仍可能更慢。
HaMeR 当前小批样本与 FP 没有证明拆分能加速单次调用，因此支持按 `split_stages` 选择，默认不启用。
profile 开销由同样输入的 baseline/profile 对照观察；三次短测量不足以对小差异作统计显著性结论。

早期实现用大量独立数组文件交接，挂载盘 IO 令 SAM2 拆分热调用中位数达到约 24.93 秒。
改为每块一个连续数组文件＋JSON、有限多帧 mask 块，再增加显式本地盘目录后显著减少开销。
这说明交接格式和存储位置也是完整执行成本，不能只展示最快的 GPU 前向数值。

输出对照检查 Parquet/NPZ 文件集合、行键/顺序/字段、mask 解码后的逐像素一致性及几何数组。
HaMeR 关节门槛 0.1 mm、相机平移 1 mm、MANO 分量 1e-3；FP 变换分量 1e-3；
Fast3R 相对坐标点值绝对差 1e-4、姿态 1e-3、内参 0.1 px，视图/源像素对应不允许变化。
这些是适配器回归门槛，不是模型真实精度或世界尺度的保证；没有因失败扩大容差。

拆分模式的单模型资源观测如下，VRAM 为冷/热全部调用的设备采样峰值，RSS 两列来自不同 runner，不能相加当同时峰值。

| 模型 | NVML 设备 GiB | GPU runner RSS GiB | CPU runner RSS GiB | 阶段 spool 峰值 MiB |
| --- | ---: | ---: | ---: | ---: |
| fast3r | 5.03 | 5.33 | 0.61 | 1.53 |
| foundationpose | 6.02 | 9.64 | 0.45 | 6.15 |
| hamer | 6.41 | 3.44 | 0.64 | 4.50 |
| sam2 | 3.09 | 3.18 | 0.44 | 0.64 |

## 实际调度矩阵

同一 8 秒、400 帧、500×282、50 fps 视频，选取 8 个不重叠的 25 帧窗口，共 200 帧／4 秒去重源视频。
每个配置都执行 SAM2 和 Fast3R，单 GPU、相同模型与输出、常驻 runner、相同线程限制与资源额度。
每种配置两次独立运行，第二轮反转配置顺序以降低顺序偏差；没有模型推理替身。
共同输出为 16 条重建视图、175 帧 mask、275 条实例及 275 条轨迹记录。其中首个窗口无分割检测，
去重源视频秒数是输入吞吐口径，不等于每帧都有目标或经过人工质量审核的有效产出。

总耗时从 Ray 启动前计到本次流水线返回及关闭，包含冷启动；不是长时间稳态吞吐。
每片段延迟从 Prepare Running 到最后模型 Writer Done，p95 用 nearest-rank；8 个片段下它接近最慢片段。
下表模型冷调用次数依据实际 model_cache_hit 统计，不把每次轻量 `_load()` 检查当成权重重载。

| 配置 | 两次总耗时 s | 中位数 s | 两次片段提交 p95 s | 两次冷模型调用数 |
| --- | ---: | ---: | ---: | ---: |
| baseline-w4 | 122.5 / 95.9 | 109.2 | 115.0 / 88.5 | 6 / 4 |
| heuristic-w1 | 201.1 / 202.4 | 201.8 | 201.1 / 201.4 | 16 / 16 |
| heuristic-w4 | 88.2 / 85.8 | 87.0 | 82.2 / 78.2 | 4 / 4 |
| heuristic-w8 | 70.4 / 70.4 | 70.4 | 62.1 / 61.6 | 2 / 2 |
| cost-all | 71.0 / 70.8 | 70.9 | 62.3 / 60.3 | 2 / 2 |
| cost-no-load | 68.0 / 65.7 | 66.8 | 57.8 / 55.3 | 3 / 3 |
| cost-no-service | 69.9 / 71.2 | 70.5 | 59.1 / 62.5 | 2 / 2 |
| cost-no-release | 71.6 / 70.8 | 71.2 | 62.7 / 61.9 | 2 / 2 |

`baseline-w4` 保持整阶段 GPU actor；`heuristic-w*` 启用拆分并改变驻留窗口；`cost-*` 启用相同拆分、
显式校准成本及最大等待保护，分别移除一个成本项。等待保护始终保留，没有用饿死分支换取吞吐。
两轮共 128 个完成片段是重复对照，不是 128 个不同视频。结果支持本机样本的比较，不足以宣称代价策略普遍优于简单 W 参数。
完整分项、队列/在途额度、实际决策、两轮资源峰值与去重视频秒数/GPU 小时均在机器摘要与原始报告中。

完整成本策略约 70.9 s，与简单 W=8 的 70.4 s 接近。移除加载项约 66.8 s，但进程树 RSS 峰值约 8.62 GiB，
高于 W=8 的 5.86 GiB；仅两次重复不能据此选出通用最优策略。基线两次重载数为 6/4，
反映就绪时序与等待保护也会影响实际批次，W 不是严格锁定的连续调用次数。

矩阵保留 prepared 文件以便追溯，所以释放项在这里表示退出活动准入统计，并不回收这些文件的物理磁盘空间。
NVML 与进程采样均未记录到其它计算 PID；这仍不排除桌面图形负载或采样间隔内的短暂峰值。

## 更长 RGB 链与可靠性

另执行完整 8 秒／400 帧视频，启用 SAM2、HaMeR 和 Fast3R，对照整阶段与拆分各一次。
首帧无检测的一次提示配置得到空手部输出，已作为负例保留；最终对照均使用 0 秒和 4 秒两次相同提示，
实际分割与手部覆盖见机器摘要的 long_coverage，不把 400 帧输入全算作有效手部输出；
它比 30 帧预检长，但不是分钟/小时序列容量验证。
两条路径共同输出 2 条重建视图、80 条手姿态、200 帧 mask、600 条实例及 600 条轨迹。
两个人手实例身份及帧范围也逐项一致；mask 覆盖源帧 200–399，手姿态采样覆盖 200–395。

| 路径 | 总耗时 s | 同时进程树 RSS GiB | 设备 VRAM GiB | work＋外部阶段块峰值 MiB |
| --- | ---: | ---: | ---: | ---: |
| baseline-w4 | 142.1 | 13.13 | 6.42 | 25.11 |
| heuristic-w4 | 138.0 | 12.51 | 6.42 | 86.11 |

调度和更长链逐片段读回 QC，并校验每个阶段收据引用文件的 SHA；同一 run 的外部阶段命名空间在结束后为空。
完整生产调度没有固定 PnP 随机源，不能把不同运行的相机数值差异一概判为拆分误差；数值等价证据来自固定 seed 的阶段对照。
质量仍为合同/几何规则与自动 QC，未新增人工标注精度评估。

最终核心/真实 Ray 回归：**248 passed，11 deselected**，耗时 214.18 s；排除项为环境/原生 smoke 标记，
真实模型另由上述 GPU 实验验证。
覆盖慢 Writer、结果/临时盘预算、CPU/GPU/CPU 跨片段重叠、输入/推理/后处理/写盘四处临时失败、
中断后清理与恢复、源身份/提交篡改、空数组/非连续数组/memmap 生命周期、丢失世界对应产物及左右手/尾批。
Ray 测试中的逻辑 GPU 仅用于控制契约；本节之前的模型/调度测量才使用真实 RTX GPU。

## 仍未实现及下一阶段重点

| 设计方向 | 本轮边界 | 下一项有意义的工作 |
| --- | --- | --- |
| 视频准备与解码 | 仍使用 clip 转码；Fast3R 保留 JPEG 官方像素语义；SAM2 官方 loader 独立 | 固定输出下对照直接源范围/顺序取帧/转码，量化编码与 IO；有证据再评估硬件解码 |
| 第五部分 B 的更广共享 | 同准备 clip、同解码身份共享；无跨重叠 clip 去重、无 SAM2 loader 共享 | 先统一或验证解码器像素，再设计源帧范围身份与消费者寿命 |
| 全机器资源预算 | 有输入缓存、阶段临时块、结果包和 prepared 准入；非 OS 硬限额 | 合并模型私有堆、页缓存、Ray spill、JPEG/debug/输出的寿命与峰值观测 |
| 第三部分控制/传输开销 | 已计序列化/写盘；仍有 Python dict/list、JSON 信箱、SQLite、小文件 | 根据短任务占比，优先去重身份计算、缩小缓存失效范围，再决定列式交接或批量状态写入 |
| 更完整的代价模型 | 单样本线性工作量、加载成本与有限释放奖励 | 多长度/分辨率/实例数校准；对热启动、CPU 瓶颈、慢盘分别检验；保留退化对照 |
| 服务器研究验证 | 只有单卡小矩阵与较长样本 | 物理 2→4→更多 GPU、长稳态、多实例 RGB-D、固定分组对照、统一模型的 Ray Data/Xenna/Data-Juicer 对照 |
| 自动资源规划 | 没有实现，符合本轮要求 | 先扩大实测和安全余量证据；当前继续只给建议，由用户显式选择配置 |

因此第三部分已从“只有风险清单”推进到可观测、可拆分、可比较的执行实现，但不能宣称全部解决。
第五部分 B 的首版机制已完成，跨视频重叠共享与统一全进程预算是明确保留的后续范围。
