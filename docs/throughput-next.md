# 第三部分：从可用性推进到可解释的吞吐优化

本页保留本轮实施前的推进依据。分项计时、四模型内部执行步骤、有预算交接、显式代价调度已落地，
当前行为与配置以 [throughput-execution.md](throughput-execution.md) 为准；本轮已完成
[R1–R7 验收](throughput-goal.md)，实测结果及未完成研究见 [验收报告](throughput-validation.md)。
以下“仍缺什么／下一步”描述的是实施前的计划，不是当前功能状态。

当前可以稳定调用阶段、提交结果、恢复任务，并通过 replay/gpu-probe 固定输入做实验。
下一步重点是回答“GPU worker 的时间花在哪里”，再决定拆哪段工作。
第五部分 B 的共享缓存只减少一类重复输入工作，第三部分的吞吐风险还没有全部解决。

## 已有机制与真实缺口

| 路径 | 现在具备什么 | 仍缺什么 |
| --- | --- | --- |
| 视频准备 | FFmpeg 提取、帧/fps 校验；共享缓存按需解码准备 clip | 直接读源范围与转码的公平对照；解码/编码/IO 分项成本 |
| SAM2 | 常驻权重，片段状态独立；官方视频 loader | 提示帧预取；union/实例 mask 的一次 D2H 与共享 CPU 编码；后处理拆分 |
| HaMeR | 官方 crop 可缓存，帧跨模型复用；逐帧 batch 不变 | CPU 提前准备 crop、有限跨帧合批、单独前向计时 |
| FoundationPose | RGB-D 按帧复用、mesh 按片段复用、tracker 独立；共享 RGB 缓存 | decode/depth/注册/跟踪/渲染分项计时；是否拆分由结果决定 |
| Fast3R | 共享采样帧，权重驻留 | JPEG 往返与官方 loader 成本；前向与 CPU PnP 分离 |
| 阶段数据 | 按列读依赖，Writer 直接消费大结果引用 | Python dict/list/RLE 转换与序列化成本；必要时换紧凑数组 |
| 控制与写盘 | 阶段提交、恢复、逐次性能历史 | 短任务下 SQLite、日志、小文件占比；普通事件合并与可靠提交的边界 |
| 资源 | 数量/结果字节反压、prepared 高水位、输入缓存预算、真实 NVML/RSS | 全进程与临时盘统一估算；2–16 卡稳态配比和尾部等待实测 |

“已接入”不表示“此处一定是瓶颈”。本机短样本不是服务器瓶颈排名；NVML 利用率是整个设备的采样信号，
不能区分具体模型的 CPU 等待与前向，也不能代替有效产出。

## 第一优先级：可比较的分项计时

以 `invocation_id / clip_id / stage / worker / trial` 关联事件，固定输入、模型版本与输出集合。
建议按以下边界补观测，先保持现有任务和恢复协议不变：

| 计时边界 | 测量方法 | 用来决定什么 |
| --- | --- | --- |
| 排队、进程启动、模型加载 | 协调端/worker 单调时钟；保留冷/热标签 | 驻留窗口是否足以摊薄加载，还是等待代价更大 |
| 视频 decode、seek、JPEG/临时文件 | CPU 墙钟 + 进程 CPU 核秒 + IO 字节；记录帧号 | 直接源读取、共享帧或硬件解码哪项值得试 |
| crop/resize/归一化/H2D | CPU 时间分别计；CUDA 传输用事件或明确同步边界 | 是否需要 CPU 预取、pin memory、有界双缓冲 |
| GPU 前向、时序推理、渲染 | 同一 CUDA stream 上的 events；边界说明同步开销 | 哪些模型的工作可以合批，哪些必须保持时间顺序 |
| D2H、mask 编码、PnP、表转换 | 分别计 CPU/墙钟，并记录数据体积 | 哪段 CPU 工作值得移出 GPU actor |
| 序列化、Writer 排队、压缩、提交 | 大结果发出/Writer 开始/提交完成事件 | 瓶颈是否已转移到结果传输或磁盘 |

不要在每一小步无条件 `cuda.synchronize()`：它会改变流水线重叠。本版 gpu-probe 在阶段边界同步，
得到的是含 CPU/加载的完整阶段墙钟；更细粒度计时应有显式诊断开关，并测开关自身的开销。
时间段可能重叠，不能把所有观测值直接相加，也不能用“总时间减已计 CPU”推断 GPU 时间。

验收时至少保留：同一短样本的冷/热分项、一个更长片段、更多手/对象、多个活跃片段、慢 Writer。
每个设置重复测量，记录中位数、离散程度、输出覆盖、RSS/VRAM/临时盘与失败，而不是只记录最快值。

## 第二优先级：选择能验证等价性的局部优化

建议按实测选择先做的一项，而不是同时改所有路径：

1. **HaMeR 有界跨帧 crop batch。** 将“读帧/官方裁剪”和“前向”分开，保留
   `(frame_index, object_id, handedness)` 回填映射；限制 crop 数和字节数，维持输出采样帧与精度。
   不足一批的尾部也必须处理。对照逐帧 batch，验证关节/相机参数、行键和有效覆盖。
   仅从 batch=1 增加到合批可能改变 GPU 内核数值，需要预先约定误差，不能仅比行数。
2. **SAM2 mask 一次搬运。** 在官方时序推理返回点保持对象身份，尽量一次得到阈值后的 CPU mask，
   从同份 mask 生成实例与可选 union；先验证逐帧 RLE 解码后像素、对象 ID、框、面积。
   再研究将 CPU 编码交给有界后处理池。不要共享/重排 predictor 的片段内状态。
3. **Fast3R 输入与 PnP 拆分。** 先计 JPEG 和官方 loader；若显著，再比较直接张量路径，
   确认 resize/crop/归一化与现有 JPEG 像素语义。前向输出转交 CPU PnP 时限制点图体积和在途块，
   并保持 PnP 失败显式报错，不能写 identity 假结果。
4. **FoundationPose 按证据推进。** 已有 RGB-D 和 mesh 复用，先测注册/跟踪/渲染和深度读取占比。
   一个对象内按时间顺序，跨对象/片段才有独立并行空间；tracker 状态不能放进共享缓存。

每项都使用 replay 固定上游，完成“输出对照＋局部时间＋完整阶段时间＋资源峰值”的单项实验后再进入整链。
缓存命中减少 decode 不保证更快：校验、memmap 读回、复制、磁盘与锁本身都有成本。

## 第三优先级：把有收益的工作移到调度边界

逻辑阶段和提交文件保持不变；执行工作可变为有界的 CPU 输入块 → GPU 调用 → CPU 后处理。
一个块可以是一批手框或有限帧，不为每个小函数建立 Ray task。
让 CPU 准备下一块、GPU 处理当前块、Writer 写上一块，收益来自资源重叠。

接入前应明确：

- 输入/结果各在哪个环节预留和释放字节，失败或重试由谁持有额度。
- Writer 在生产侧预算满时仍能排空；不能形成“等 Writer 空位才能释放 Writer 所需资源”的循环等待。
- GPU 槽位何时可复用，哪些 CPU 数组/引用仍存活；移出 CPU 后处理不能遗漏异步 GPU 工作。
- 阶段仍在最终 Writer 确认后才提交/解锁下游；中间块默认是可丢弃输入，不伪装成可靠阶段完成。
- SAM2/FP 的状态只在所属片段内使用；进程复用只复用权重，时序状态仍重建。

CPU/临时盘预算先分项记录，再做总量准入。当前 input cache 的磁盘上限不能代表所有 JPEG、
转码、debug、结果、页缓存和进程堆，也不能直接拿某个 Torch 峰值推算单卡共驻四个模型。

## 调度研究随后推进

现有基线是一个 Ray Core 后端、共享 GPU 池/可选人工阶段组、每卡串行、同模型偏好、
`model_residency_tasks` 驻留窗口、`max_stage_wait_s` 等待保护，以及数量/字节反压。
它尚未按预检报告自动分配 worker，也没有学习式/代价驱动决策、抢占或多模型显存共驻保证。

在分项计时可信之后，才用数据比较：

- W=1/4/8 的驻留窗口是否减少加载，又是否增加 p95 等待和中间态占用。
- 相同资源下，固定阶段分组与共享池的队列/闲等差异。
- 在硬约束与等待保护后，加入切换代价、服务时间、预计释放字节的规则是否改善总完成时间。
- 每次只加入一个代价项并做消融；没有稳定收益时保留简单策略。

评价主指标应是固定质量要求下的去重视频秒数/GPU 小时、总完成时间和尾部等待，
辅以加载次数、Writer 积压、RSS/VRAM/磁盘峰值及故障恢复。一个短片段的 GPU 利用率上升不是研究结论。
正式多卡扩展与外部框架对照仍见 `design.md` 第十一部分，当前没有完成这些实验。
